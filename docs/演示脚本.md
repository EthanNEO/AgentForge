# AgentForge 2.0 演示脚本（3 分钟）

> 对应 2026-11-03 当前页面与软件交付场景。录制前必须用全新 Run 走通一次。

> ⚠️ **已被取代（历史备选）**：本脚本基于 2026-11-03 的预置场景离线演示。**主演示请用 [`演示脚本-自愈主线.md`](演示脚本-自愈主线.md)**（多 Agent 协作 + 平台独立核算 + 自愈，最贴合赛题红线）。工作台已移除场景选择器，预置场景（软件交付 / AIOps）现仅经 API 触发；下文已删除不存在的 UI 操作。

## 一、演示前准备

1. 确认 8000 端口没有旧版服务占用。
2. 在项目根目录执行 `run.bat`。
3. 打开任务工作台：`http://127.0.0.1:8000/workbench`。
4. 另开编排监控台：`http://127.0.0.1:8000/`。
5. 预置场景现经 API 触发（`POST /api/run`，`scenario:"software_delivery"`）；工作台已移除场景选择器，默认自由任务。保持默认离线回放模式。
6. 不使用旧截图或旧 PPT；现场页面就是当前版本证据。

## 二、三分钟分镜

### 0:00–0:20｜产品定位

画面：任务工作台首页。

话术：

> AgentForge 不是单个 Agent，而是管理一组 Agent 完成交付的 Harness。它负责把任务规划成 DAG，动态选择执行者，用独立验证拦截错误，并在失败后自动归因、改派和重试。

### 0:20–0:45｜生成并审阅计划

操作：输入“实现一个 CSV 数据清洗与统计 CLI 工具，生成测试、风险报告和交付结论”，点击“生成计划”。

画面重点：计划卡片显示 6 个节点。

话术：

> 系统不会直接开跑。它先生成可审阅的结构化计划。需求解析之后，测试设计和风险审查并行，编码必须等待两条分支完成。

操作：点击“确认并开始执行”。

### 0:45–1:15｜从用户工作台看执行

画面：中间进度与右侧运行信息、验证摘要、Token、成本和产物区域。

话术：

> 确认后才创建 Run。每次尝试都有独立 Worker Session、工作目录、Agent 和截止时间。用户在这里看简化进度；需要工程证据时，可以带着同一个 Run ID 进入监控台。

操作：点击“打开编排监控台”。

### 1:15–1:50｜展示真实失败与自愈

画面：监控台 DAG、Worker 列表、事件流。定位编码节点首轮验证失败、Self-Loop 和改派事件。

话术：

> 首轮低成本编码 Agent 的结果会真实运行 unittest，并被确定性验证拒绝。系统把失败归因为逻辑缺陷，记录失败证据和反馈补丁；Scheduler 对失败 Agent 降级，Optimizer 选择备用 Agent，再发起下一次尝试。

强调：

> 这里的测试、数据库状态和健康检查标记为 deterministic；默认生成内容标记为 replay。我们不会把离线回放伪装成在线模型推理。

### 1:50–2:20｜验证、并行与可观察性

画面：`supervisor.batch`、两个并行 Worker、`verification.completed`、Session ID 和来源标记。

话术：

> Supervisor 会一次派发所有依赖就绪节点，当前单批最多并行三个。生产 Session 和验证者身份分离。事件按 ID 持久化，并能关联 Run、节点和 Session；兼容轨迹与统一事件在同一个事务中写入。

### 2:20–2:40｜最终交付与继续修改

操作：返回任务工作台，展示成功状态、最终验证和产物列表。在输入框补充“再增加一条金额上限校验”。

话术：

> 完成后用户可以查看最终产物并继续提出修改。当前轻量工作台会把补充要求组合成一个新的 Run，完整的服务端对话线程是下一阶段能力。

### 2:40–3:00｜跨场景与收尾

画面：经 API 触发的 AIOps 预置 Run（工作台与监控台均无场景选择器入口）。

话术：

> 同一套 Harness 还运行 AIOps 故障处置：只调超时的治标方案会被健康检查拒绝，必须修复连接池、超时和副本数才能通过。AgentForge 的价值是让多 Agent 的执行过程可计划、可验证、可恢复、可追踪。

## 三、评委常见问题

### “这是不是写死的演示？”

默认产出是场景离线回放，这是为断网评审准备的；但 DAG 调度、并行 Worker、SQLite 状态、unittest、健康检查、失败归因、重试和事件持久化都真实执行，并通过来源标记区分。

### “L2/L3 是模型评审吗？”

当前不是。L2 是本地启发式质量评分，L3 是覆盖度或独立回归检查。在线模型评审仍是扩展方向。

### “多个 Run 会不会互相影响？”

每个 Engine 有独立 Scheduler 和 Run 目录，临时负载、成败与熔断状态不共享；累计 Agent 统计保存在 SQLite 中用于展示。

### “为什么需要两个页面？”

任务工作台服务普通用户的输入—确认—结果闭环；监控台提供比赛和工程排障需要的 DAG、Worker、验证、反馈和事件证据。两者共享同一后端，不是两个应用。

### “能否用于生产？”

当前是单机比赛原型。生产化还需要容器隔离、权限、多租户、持久化对话、取消/人工接管、压力测试和崩溃恢复。
