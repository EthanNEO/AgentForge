# 项目白皮书 · AgentForge 多智能体编排与验证平台

> 版本 3.0｜2026-11-16
> 本文只描述当前代码可运行、可观察或可测试的能力。

## 一、项目概述

### 1.1 背景

单个 Agent 能生成内容或调用工具，但工程交付还需要回答：任务如何拆分、由谁执行、依赖如何控制、结果如何验收、失败如何恢复、过程如何审计。AgentForge 针对这些问题提供任务级多智能体 Harness。

### 1.2 定位

AgentForge 不是新模型，也不是聊天外壳。它位于用户任务与底层 Agent/模型之间，负责：

- 把任务转换为结构化 DAG；
- 按角色、能力、运行状态和成本选择 Agent；
- 在独立 Worker 会话中执行；
- 用确定性证据验证产出；
- 对失败归因、反馈、改派和重试；
- 持久化计划、事件、验证、产物和经验。

### 1.3 当前产品形态

同一个 Web 应用包含两个入口：

1. **任务工作台**：面向普通用户，完成输入任务、预览计划、确认执行、查看进度与结果、继续补充要求。
2. **编排监控台**：面向开发者、管理员和比赛演示，展示 DAG、Worker Session、调度评分、验证证据、失败反馈、事件与成本。

两页共享后端 Run 数据，无需制作两个桌面应用。

## 二、解决方案

### 2.1 执行闭环

```text
任务 → 计划预览 → 用户确认 → 多 Agent 执行 → 独立验证
    → 失败归因与改派 → 成功交付 → 用户补充要求或查看监控证据
```

Planner 在执行前验证 DAG；Supervisor 派发所有依赖就绪节点；Scheduler 在每个 Run 的独立状态中选 Agent；Worker 使用独立目录和工具策略；Verifier 与产出 Session 分离；Optimizer 依据验证报告决定下一步。

### 2.2 六项核心能力

1. **知识集成**：SQLite 文档库 + 零依赖 BM25 检索，节点执行前检索相关规则。
2. **Agent 团队定义与配置**：角色、模型、能力、成本和工具配置化；`/api/agents` CRUD + 监控台「Agent 配置」面板（创建/编辑/停用/删除、成功率/成本/连续失败/降级熔断、调度选择理由因子分解）。
3. **工作流编排**：模型按复杂度自由生成 DAG（1–5 节点）+ 平台补齐 analyst→coder→tester→reviewer；版本化 DAG、依赖/环校验、并行就绪节点和节点重试预算；平台核算任务强制单节点。
4. **动态调度**：能力、当前 Run 成功率、负载、成本四维评分，连续失败触发降级与熔断。
5. **结果验证**：L1 确定性检查、L2 启发式质量评分、L3 覆盖度/回归复核；**平台独立核算**（报名/会议室/AA/CSV 预期由平台确定性计算）+ **真实浏览器验收**（页面行为断言）。
6. **反馈优化**：六类失败归因、结构化重试决策、Agent 改派和跨 Run 经验复用；自愈演示主线（注错→核算拒绝→归因→携带证据修复→通过）。

### 2.3 可信与可观察

- 每次尝试都有 Session ID、Agent、工作目录、截止时间和来源。
- trace 与 event 同事务写入，避免一次事件只留下半份记录。
- 事件支持游标轮询，可关联 Run、节点和 Session。
- 最终产物仅从 Run 的 `artifacts` 目录列出，路径解析拒绝越界和符号链接。
- `deterministic`、`replay`、`model` 分开标记，避免把离线演示内容描述成在线模型结果。

## 三、场景验证

### 3.1 软件交付

当前 DAG 包含 6 个节点：需求解析后，测试设计与风险审查并行；两者通过后进入编码实现、边界加固和交付评审。

默认离线演示中，首版代码真实运行 unittest 并出现失败。系统将其归因为逻辑缺陷，记录经验、改派 Agent，再次生成并通过确定性测试。这个场景证明的不是“模型一定正确”，而是错误能被发现、解释和恢复。

### 3.2 AIOps 故障处置

当前 DAG 包含 5 个节点：告警分诊、根因定位、处置执行、恢复验证、复盘沉淀。模拟服务初始存在连接池过小、超时过低和单副本问题。只调整超时的首轮修复会被健康检查拒绝；完整修复后才能进入复盘。

### 3.3 可迁移性

两个场景共用同一 Planner、Supervisor、Scheduler、Engine、Validator、事件协议和双页面。新增场景主要通过一个 Python 场景模块声明节点、离线产出与验证配置。

### 3.4 自由任务多 Agent 协作与平台核算（竞赛主证据）

- **多 Agent 协作**：复杂自由任务由模型规划为多节点 DAG。实机 Run `20261116-112627-f43a61e1`：需求分析→实现→测试→交付评审，4 节点 4 角色真实执行，3 条产物交接（analysis.md / index.html / test_report.md），编码与测试节点含自愈重试。
- **平台独立核算盲测**：固定 Harness、钉住规划模型，业务通过 = 平台核算用例全部通过。最新 deepseek 5 任务 5/5（`output/eval-blind-20261116-114104.md`）；跨模型对照 qwen 20% / deepseek 80% / mimo 80%（`output/eval-blind-20261116-094116.md`），证明验证客观性而非模型自评。
- **自愈主线**：Run `20261116-113735-2c8e4efa`，首版注错（历史真实错账页面，provenance=demo）→平台核算拒绝（140/200、80/200 错账）→`LOGIC_DEFECT` 归因→携带证据修复（attempt 2）→2/2 通过，`narrative_complete=true`。核算/归因/修复全部真实执行，不伪造验收。

## 四、实现与证据

### 4.1 技术栈

- Python 标准库 HTTP 服务与执行内核；
- SQLite 持久化；
- 原生 HTML/CSS/JavaScript 双页面；
- unittest 自动化验证；
- 可选 OpenAI 兼容模型接口。

### 4.2 当前测试基线

**179 项自动化测试**（14 个测试文件）覆盖规划、策略、超时判定、并行就绪节点、Run 隔离、事件事务、事件游标、计划预览、Run ID 唯一性、产物路径安全，以及 API 契约、模型网关、平台核算验收（报名/会议室）、前端契约、function tools、自愈竞赛特性、上传、启动器等。已具备真实浏览器验收、前端契约测试、完整 HTTP 端到端契约测试与真实在线模型盲测；高并发与崩溃恢复仍需继续补充。真实浏览器断言：主题一致性 16/16、多节点 DAG 8/8、自愈叙事 10/10、Agent 面板 6/6、分栏拖拽 13/13。

### 4.3 运行方式

默认离线模式不依赖网络和 API Key，Windows 执行 `run.bat` 即可启动。任务工作台位于 `/workbench`，编排监控台位于 `/`。

## 五、创新点与价值

### 5.1 从“生成”转向“交付控制”

平台把关注点从一次回答扩展为计划、执行、验证、恢复和证据链，适合代码交付、数据处理、运维处置等需要明确验收的任务。

### 5.2 可解释的质量与成本权衡

调度评分和候选排序可见；廉价 Agent 可以先尝试，验证失败后再升级到高能力 Agent。验证失败原因、重试次数、Token 和估算成本都被记录。

### 5.3 离线可演示、在线可扩展

离线回放保证比赛现场稳定，真实测试和健康检查保证验证证据仍可复现；在线模式则允许接入兼容模型。来源标签使两种模式不会混淆。

### 5.4 平台独立核算：把验收权从模型手里拿走

多数 Agent 方案让模型自评，容易“自我感觉良好”。AgentForge 把验收权交给平台：预期结果由确定性规则独立计算（如 AA 转账按整数分平摊），页面行为由真实浏览器断言。错误是被平台客观拦下的，再携带证据修复——这是“验证创新”的核心，也是跨模型盲测通过率差异的来源。

## 六、当前边界

- 工作台不是完整 IDE，暂无项目文件树、终端和 Git 操作。
- 继续追问会创建新 Run，暂无服务端持久化聊天线程。
- 自由任务 DAG 由模型按复杂度生成（预置场景由代码定义），暂无可视化流程编辑器。
- Worker 是目录/策略隔离，不是生产级容器沙箱。
- 暂无用户体系、多租户、远程部署、分布式 Worker 和人工审批队列。
- Watchdog 目前负责超时判定与事件，不承担跨进程强杀和孤儿进程回收。
