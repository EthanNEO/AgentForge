# AgentForge 自愈主线演示脚本（3 分钟）

> 对应 2026-11-16 竞赛整改后的真实能力：平台独立核算拒绝 → 失败归因 → 携带证据修复 → 通过。
> 已用全新 Run 端到端走通：`20261116-113735-2c8e4efa`（在线模式，约 70 秒，2/2 平台核算用例通过）。
> 红线：不伪造验收。演示中唯一「注入」的是首版产物（历史真实错账页面，provenance=demo 全程标注）；
> 核算拒绝、归因、模型修复全部真实执行。

## 一、演示前准备

1. 启动服务（在线模式，需已配置模型密钥）：`cd backend; python -m app.launcher --port 8000 --no-browser`。
2. 打开任务工作台：`http://127.0.0.1:8000/workbench`。
3. 另开编排监控台：`http://127.0.0.1:8000/`。
4. 一键复现（可选，含截图与证据报告）：
   `cd backend; python demo_selfheal.py --port 8000 --resume --shots`
   - 输出逐步界面状态与 URL；结束生成 `output/demo-selfheal-<时间戳>.json` 证据报告；
   - `--shots` 在失败态与终态对两个入口真实截图（`output/demo-selfheal-shots-<时间戳>/`）；
   - `--resume` 若两次尝试后仍失败，自动走平台「从未完成步骤继续」携带证据续跑再验一遍。
5. 素材溯源：注入的错账页面来自历史运行 `20261116-012851-5870d071` 的真实产物
   （`backend/app/demo_assets/aa_faulty_index.html`，SHA256 与原件一致）。
   该页面初始化时预载演示费用，导致新录入叠加算出 140/200 错账——正是当初被平台核算拦下的实现。

## 二、三分钟分镜

### 0:00–0:25｜产品定位与演示入口

画面：任务工作台首页，左侧「🔁 自愈演示」按钮。

话术：

> AgentForge 是管理一组 Agent 完成交付的 Harness：规划 DAG、动态调度、独立验证、失败归因与自愈。
> 今天演示它最核心的一条主线——错误不是被模型自己「感觉」发现的，而是被平台独立核算客观拦下，再携带证据修复。

操作：点击「🔁 自愈演示」。

### 0:25–0:50｜计划审阅：平台核算用例 + 注错声明

画面：计划卡片。顶部琥珀色「自愈演示（注错）」横幅写明来源运行与「核算/归因/修复全部真实执行」；
验收要求中包含平台独立核算的转账用例（预期金额由平台按整数分平摊计算，不采信模型手算）。

话术：

> 计划先经人确认。两条关键用例的预期转账是平台自己算的：小李垫付 300 元三人平摊，小王、小张各转 100；
> 多笔场景同样由平台核算。演示会注入一份历史真实错账实现作为首版——注入本身在事件流里明确标注 demo，绝不冒充模型产出。

操作：点击「确认并开始执行」。

### 0:50–1:30｜平台核算拒绝（可见失败）

画面：工作台进度卡片 + 自愈叙事卡片第①步「平台核算拒绝」（红色）；展开「查看平台核算证据」：

> 验收第 2 条未通过：预期转账 小红转给小李 100 元；小王转给小李 100 元，
> 实际 小王转给小李 140 元；小张转给小李 100 元；小红转给小李 100 元

操作：切到监控台（同一 Run ID），事件流可见 `demo.fault_injected`（warning，provenance=demo）→
真实浏览器验收 → `verification.completed`（拒绝，附证据）→ `selfloop`（失败归因）。

话术：

> 首版页面在真实浏览器里被操作：录入、点击、读取结果。平台把实际转账和独立核算的预期逐笔比对——
> 140/200 的错账被客观拒绝，证据精确到「预期多少、实际多少」。这不是 LLM 评 LLM。

### 1:30–2:10｜归因与携带证据修复（可见自愈）

画面：叙事卡片第②步「失败归因：逻辑缺陷 · 策略：失败用例驱动修复」；
监控台 `optimizer.decision`（switch_agent）与 Scheduler 候选排序、选择理由；
第③步「携带证据修复」展开可见修复指令节选——逐条失败用例、预期/实际对照都写进了下一轮提示词。

话术：

> Self-Loop 把失败归因为逻辑缺陷，生成携带完整失败证据的修复指令；Optimizer 改派更合适的编码 Agent。
> 第二次尝试不是重来一遍，而是带着「哪条用例、预期什么、实际什么」去精准修复。
> 注意：注入导致的首次失败不计入 Agent 统计——降级只针对真实模型失败，演示不污染调度数据。

### 2:10–2:45｜验收通过（可见闭环）

画面：叙事卡片第④步「验收通过：平台核算用例 2/2 全部通过」；
工作台验收摘要、产物区可下载修复后的 index.html；监控台 DAG 节点变绿、运行状态 succeeded。

话术：

> 修复后的页面再次被真实浏览器操作、被平台独立核算——2/2 用例通过，任务成功。
> 失败 → 归因 → 修复 → 通过，每一步都有界面状态和持久化证据。

### 2:45–3:00｜收尾：证据可复现

画面：`output/demo-selfheal-*.json` 报告与四张截图。

话术：

> 整条主线一条命令可复现，证据报告记录每个环节的 Run ID、用例预期、拒绝证据、归因代码与通过数。
> 同样的机制也用于真实任务：复杂任务会被规划成多角色 DAG，失败同样走这条自愈链路。

## 四、常见问题

- **为什么注入首版？** 真实模型首版不一定恰好犯错；注入历史真实错账页面保证演示必然触发「拒绝→修复」主线，
  且注入全程标注 demo。验收、归因、修复没有任何伪造。
- **注入失败会降级 Agent 吗？** 不会。引擎对注入尝试跳过失败统计（`injected` 分支），调度数据只反映真实模型表现。
- **修复仍失败怎么办？** 脚本 `--resume` 自动走平台「从未完成步骤继续」，携带失败证据续跑；
  真实运行 `20261116-112230-b8b17b74` → 续跑 `20261116-112627-f43a61e1` 即此路径的实证。
- **离线模式能演示吗？** 不能。演示端点要求 live 模式（真实修复需要在线模型），mock 下直接拒绝并说明原因。
