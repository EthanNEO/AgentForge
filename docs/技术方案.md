# AgentForge 2.0 技术方案

> 本文以 2026-11-16 的代码和自动化测试为准（179 项测试）。规划中但尚未实现的能力不计入现状。

## 1. 目标与定位

AgentForge 是任务级多智能体 Harness，负责“规划、分派、执行、验证、恢复和留痕”。它不替代底层模型，也不把单次模型输出直接视为交付结果，而是通过可复现验证和结构化反馈控制整个 Run。

当前版本面向本地演示和初赛验证：默认离线、零安装、单机运行；配置环境变量后可由 ModelGateway 真实调用 **qwen / DeepSeek / Xiaomi MiMo 三个 Provider**。生产级沙箱、账户和分布式 Worker 均不是默认能力。

## 2. 系统分层

```text
交互层     任务工作台 / 编排监控台
API 层     标准库 HTTP Server / Router
规划层     Planner / ExecutionPlan / DAG 校验
监督层     Supervisor / Scheduler / Watchdog
执行层     Worker Session / Context / ToolPolicy / 场景适配器
验证层     Validator / VerificationReport / Optimizer / Self-Loop
记忆层     BM25 Knowledge Base / Experience Memory
持久化层   SQLite / Run Artifacts / Typed Events
```

## 3. Run 生命周期

1. `POST /api/plan` 根据任务和场景生成只读计划预览，不创建 Run。
2. 用户确认后，`POST /api/run` 创建唯一 Run ID，并由后台线程执行。
3. Planner 将场景节点转换为 `ExecutionPlan`，检查重复 ID、未知依赖和环。
4. Supervisor 从节点状态中找出全部依赖就绪节点。
5. Engine 使用最多 3 个线程并行执行同批就绪节点。
6. Scheduler 选择 Agent；每次尝试建立独立 Worker Session 和目录。
7. Worker 产出先写入尝试目录，再提升到 Run 的最终产物目录。
8. Verifier 对最终目录执行验证；失败后进入归因、决策和重试。
9. 全部节点通过则 Run 为 `succeeded`；节点耗尽重试或引擎异常则为 `failed`。

当前代码实际使用的终态是 `succeeded` 和 `failed`；`cancelled`、人工接管状态和暂停/恢复尚未接入 HTTP 控制面。

### 3.1 HTTP API 面（2026-11-16）

除 `POST /api/plan`（只读预览）、`POST /api/run`（创建并后台执行）、`GET /api/runs/{id}`、`GET /api/runs/{id}/events` 外，新增：

- `POST /api/runs/{id}/retry-plan`：从未完成步骤携带证据续跑（`reuse` 可复用已通过节点）。
- `/api/agents` CRUD（`GET`/`POST` 列表与创建、`GET`/`PUT`/`DELETE` 单个）+ `GET /api/agents/rank?role=`：Agent 定义配置与调度排序视图（含选择理由因子分解）。
- `POST /api/demo/selfheal`：自愈演示端点（要求 live 模式；真实规划 + 平台核算用例 + 首版注错，核算/归因/修复全部真实执行）。
- 草稿恢复与澄清门槛：规划预览支持澄清问题与草稿恢复；附件上传经 `uploads.py`。

## 4. 规划与并行监督

### 4.1 结构化计划

`PlanNode` 包含节点 ID、名称、角色、依赖、输出、验证器、最大尝试次数和扩展配置。`ExecutionPlan` 保存场景、任务、模式、版本和来源。

Planner 现在支持**模型自由生成 DAG**：自由任务（`scenario:"custom"`）由规划模型按任务复杂度生成 1–5 节点的计划，平台再做 DAG 完整性与环校验。复杂度判定（`COMPLEXITY_CUES` / `_is_complex_task`）识别多交付物、分析+实现+测试、明确分步等线索；复杂任务要求多节点 DAG，模型仍给单节点时由 `_expand_complex_plan` 补齐 analyst→coder→tester→reviewer（含节点 ID/文件名碰撞保护，原节点验收与浏览器用例不动）。报名/会议室/AA/CSV 等**平台核算任务强制单节点**（`_is_platform_simple_task`），以保证 grounding 契约稳定。预置场景（如 `software_delivery` 6 节点）仍从代码定义生成计划，作为多 Agent 协作参照。计划持久化 `complexity` 判定（线索/理由/是否扩展），工作台与监控台均显示判定横幅。

### 4.2 Supervisor

`ready_nodes()` 返回尚未执行且全部依赖已通过的节点。软件交付场景中，需求解析完成后，“测试设计”和“风险审查”会同时就绪并并行执行；编码节点等待两者全部通过。

### 4.3 Watchdog

每个 Worker Session 保存 `started_at` 和 `deadline`。生成返回后，Watchdog 比较当前时间与截止时间，超时则记录 `watchdog.timeout` 并进入重试反馈。它是任务内超时判定机制，不是跨进程守护服务，也不会强杀任意远程 Worker。

## 5. 动态调度

调度评分：

```text
score = 0.40 × capability
      + 0.25 × session_success_rate
      + 0.20 × (1 - load)
      + 0.15 × (1 - normalized_cost)
      - breaker_penalty
```

- `capability`：Agent 对角色的能力先验。
- `session_success_rate`：当前 Run 内经拉普拉斯平滑的成功率。
- `load`：当前 Run 内该 Agent 的占用量。
- `normalized_cost`：相对成本上限的归一化值。
- `breaker_penalty`：连续失败一次降级 0.25，两次熔断 0.55。

每个 `Engine` 自建 `Scheduler`，因此并发 Run 不共享临时统计和 inflight。数据库中的累计成功/失败仅用于 Agent 面板展示和持久化观察。

## 6. Worker、上下文与工具策略

每次尝试生成稳定的 Session ID，并写入：

```text
data/runs/{run_id}/workers/{node_id}/attempt-{n}/
```

上下文只包含任务、当前节点、声明依赖的上游产物、知识库命中、上一轮反馈，以及最多 3 条同节点历史经验。角色通过 `ToolPolicy` 获得读、检索、写、测试或脚本执行权限；路径解析必须保持在目标工作目录内。工具集（`function_tools.py`）含 `write_file`、`append_file`（分块写入，同策略鉴权/产物白名单/200k 上限，用于规避单次输出长度上限）、`read_file`、`list_files`、`run_tests`、`kb_search`、`run_script`。输出长度/预算/轮数上限时，引擎提交已写出的候选产物兜底（`llm.candidate`），避免整次尝试作废。

该隔离属于目录和策略级隔离，不等同于容器、虚拟机或操作系统级安全边界。

## 7. 验证与反馈闭环

### 7.1 三级验证

| 级别 | 当前实现 | 来源 |
|---|---|---|
| L1 | JSON/schema、语法、真实 unittest、脚本和健康检查 | `deterministic` |
| L2 | 本地启发式质量评分，阈值 60 | `deterministic` |
| L3 | 验收条目覆盖度或独立回归，阈值 0.75 | `deterministic` |

当前 L2 不是在线“模型裁判”。`VerificationReport` 强制 reviewer ID 与 producer session ID 不同，用于避免产出者自评自过。

**差异化核心：平台独立核算 + 真实浏览器验收。** 在三级验证之上，报名/会议室/AA/CSV 等任务的预期结果由平台按确定性规则独立计算（如 AA 转账按整数分平摊），不采信模型手算；规划阶段经 grounding 钩子（`_ground_signup_checks` / `_ground_meeting_checks` / `ground_aa_demo_cases`）把平台核算用例写入验收。页面类任务由 `browser_check.py` 用真实浏览器执行断言（转账/名单/roster/冲突检测），验证页面实际行为而非源码字符串。盲测以“平台核算用例全部通过”为业务通过判据，客观拦下错误实现。

### 7.2 失败归因

已实现六类归因：`LOGIC_DEFECT`、`OUTPUT_INVALID`、`SPEC_GAP`、`QUALITY_GAP`、`TOOL_TIMEOUT`、`ROOT_CAUSE_MISS`。每类映射到不同反馈补丁和是否换 Agent 的建议。

Optimizer 根据验证报告、当前尝试、预算和候选排序，返回 `accept`、`switch_agent`、`revise_context` 或 `needs_attention` 决策。Engine 当前在预算耗尽时将 Run 置为 `failed`，尚未提供独立的人工接管队列。

### 7.3 经验复用

失败经验以 `node_id:attribution` 为签名写入 `lessons`。相同签名增加命中次数；后续 Run 的同类节点检索命中后，会发出 `experience.applied` 事件并把补丁加入提示上下文。

## 8. 数据一致性与安全

SQLite 表：

| 表 | 内容 |
|---|---|
| `agents` | Agent、角色、模型、能力、成本与累计统计 |
| `kb` | 知识文档及标签 |
| `runs` | 任务、场景、状态、统计和版本化计划 |
| `steps` | 每个节点每次尝试及验证结果 |
| `worker_sessions` | Session、工作目录、状态、截止时间和来源 |
| `traces` | 兼容旧监控台的可读轨迹 |
| `events` | 可按游标读取的统一类型事件 |
| `lessons` | 失败归因、策略、反馈补丁和命中次数 |

`Engine.emit()` 在同一 SQLite 事务中写入 trace 与 event，任何一项失败都会整体回滚。产物下载使用真实路径解析，拒绝符号链接、目录逃逸和非最终产物目录文件。

## 9. 可观测性

事件包含递增 ID、Run、节点、Session、kind、source、provenance、payload 和时间。主要事件包括：

- `plan.created`、`supervisor.batch`
- `worker.started`、`worker.completed`
- `tool.authorized`、`artifact`、`artifact.handoff`（上游产物沿依赖边交接）
- `verification.completed`、`validate`
- `optimizer.decision`、`selfloop`
- `experience.applied`、`watchdog.timeout`
- `llm.candidate`（上限兜底候选）、`demo.fault_injected`（演示注错，provenance=demo）、调度候选排序与选择理由
- `state`、`summary`

`GET /api/runs/{id}/events?after=N` 支持增量轮询，单次上限 500 条；Run 详情同时提供计划、节点、Worker、验证、反馈循环、轨迹、经验和最终产物元数据。

## 10. 运行模式

- **mock / replay**：默认模式。场景模块产生确定性内容，验证器仍真实执行测试或健康检查。
- **live / model**：任一真实 Provider Key 配置后启用。ModelGateway 使用标准库调用 OpenAI 兼容接口，支持 **qwen / deepseek / mimo 三个 Provider**，含递增冷却、降级与跨模型 fallback 留痕。
- **在线失败**：记录为 Worker 失败并进入现有重试/改派链路；不会生成回放产物冒充模型结果。

因此“验证是真的”不代表“默认产出来自在线模型”；两者通过 provenance 明确区分。

ModelGateway 使用独立的 `MDATAPLUS_API_KEY`（qwen）、`AF_DEEPSEEK_*` 与 `AF_MIMO_*` 环境变量，`AF_DEFAULT_PROVIDER` 选择默认 Provider；API 和事件只暴露 Provider 是否已配置、Base URL 和默认模型，不暴露密钥。调度器选择 Agent/模型，网关负责把请求路由到对应 Provider。

## 11. 测试现状

当前 **179 项 unittest**（14 个测试文件）覆盖：计划环检测、计划版本、工具权限、路径越界、Watchdog、并行就绪节点、依赖阻断、事件顺序与游标、计划持久化、上下文依赖、Optimizer 改派、Run 级调度隔离、trace/event 原子回滚、计划预览、产物范围、Run ID 唯一性、符号链接拒绝；以及 API 契约、模型网关（冷却/降级/fallback）、平台核算验收（报名/会议室）、前端契约、function tools（含 append_file）、自愈竞赛特性（复杂度规划/Agent CRUD/演示注入）、上传、启动器、GitHub MCP 等。

已具备真实浏览器验收（`browser_check.py`）、前端契约测试（`test_frontend_contract`）、完整端到端 HTTP 契约测试（`test_api_contract`）与真实在线模型盲测（`eval_blind.py`）。仍缺少进程崩溃恢复与高并发压力测试。

`model_smoke` 场景提供最小真实在线验收：单个模型 Worker 生成结构化产物，经过工作区写入、事件留痕和独立 Schema 验证；mock 模式不会生成替代产物。完整软件交付在线链路已经验证到代码执行与失败改派，当前尚不支持在测试自身有缺陷时自动回退到上游测试节点重新规划。

## 12. 当前边界与后续方向

1. 对齐并自动化测试产物元数据 URL 与实际下载路由。
2. 增加持久化对话、人工确认/驳回和暂停/取消 Run。
3. 把 Watchdog 扩展为可终止进程、回收孤儿 Session 的监督器。
4. 增加容器级执行隔离、资源配额和更严格的工具审计。
5. 增加端到端、并发和崩溃恢复测试。
6. 项目功能与视觉定稿后，重新制作 UI 截图、PPT 和演示视频。
